CubiQo Phase B Master Doc

One Durable Agentic Operator After Capsule Approval

Phase B begins when Phase A has produced a trusted RGY capsule and the user approves it. CubiQo becomes one durable operator: it creates a Duo project, builds a task graph, chooses risk-aware routes, performs safe work, pauses for approvals, logs evidence, writes outcomes, and self-heals through sandboxed proposals.

Governing Principles

The model proposes. Systems govern.

Phase B is powerful only because the LLM is not allowed to directly invoke tools. Deterministic layers validate, route, approve, budget, log, and stop unsafe work.

1. LLM proposes

  • Goal interpretation.
  • Task graph suggestions.
  • Route recommendations.
  • Drafts, questions, and summaries.

2. Deterministic systems govern

  • Permissions, connector availability, and routing validity.
  • Policy, risk, budget, retry, and security gates.
  • Approval gates and irreversible-action blocks.
  • RLS, audit logs, trace IDs, and evidence storage.
Canonical control chain: LLM planner -> Decision Router -> Policy Engine -> Execution Engine -> Evidence Layer.

Decisioning Layer

How CubiQo chooses the optimal method

The decisioning layer prevents CubiQo from going in circles or picking risky automation. It scores every possible route before acting.

Route preference order

1. Official APIBest when user OAuth/token exists and platform supports the action.
2. Plugin / MCPStructured methods with typed inputs and observable outputs.
3. ExtensionBest for authenticated user-session workflows where headless is risky.
4. Stagehand / BrowserbasePreferred unknown-UI browser layer before raw headless scripts.
5. Visible browserUser can watch, intervene, and press final buttons.
6. HeadlessOnly for low-risk public/owned/admin pages.
7. Computer useFor unknown visual UI when DOM paths are unavailable.
8. Manual askWhen risk, missing auth, or policy boundaries make automation unsafe.

Scoring factors

  • Reliability and success evidence.
  • Auth availability and connector status.
  • Platform policy and account blocking risk.
  • Data sensitivity and privacy risk.
  • Reversibility and final-action impact.
  • User approval need.
  • Provider/API/browser cost.
  • Speed and timeout risk.
  • Whether the method can prove it worked.
  • Loop risk and escalation threshold.

Governors

What stops CubiQo from becoming chaotic

These are deterministic gates around the operator. They are not optional polish; they are what make broad agentic execution safe enough to ship.

Budget governor

  • Checks estimated cost before paid external calls.
  • Writes budget_events with trace_id and provider.
  • Pauses when project/user/provider limits are hit.
  • Uses fair-use / agentic credits, not vague unlimited.

Security breaker

  • Blocks scope exceeded, rate spikes, cost spikes.
  • Flags prompt injection and exfiltration risk.
  • Kills repeated failure loops.
  • Blocks headless on risky platforms.

Policy engine

  • Validates tool call schemas before execution.
  • Checks connector scopes and action allowlists.
  • Requires approval for irreversible steps.
  • Writes audit records with route and evidence.
Realtime And Locks

How Duo Mode stays live and safe

The dashboard should feel alive while preventing two tasks from editing the same outside resource.

Streaming + realtime

  • stream_events are append-only and trace-linked.
  • Frontend subscribes by project_id.
  • Timeline updates as tasks plan, execute, pause, fail, recover.
  • Approval cards appear from data, not hardcoded screens.

Resource locks + concurrency

  • Acquire a lock before any external write.
  • No two tasks write the same Shopify product, Git branch, or deployment at once.
  • Max active projects per user and max parallel tasks per project.
  • Anti-loop: max attempts per route and total attempts per task.

Acceptance Criteria

What each slice must prove

B-Core

Capsule opens Duo Mode, project is created, trace_id is assigned, task graph is visible, route is selected with rejection reasons.

B-Execution

Queued task survives restart, checks connector readiness, executes safe steps, logs evidence, pauses for approval, and writes outcome.

B-Ops

Daily self-report is generated, failed cron/background work is detected, self-heal proposal is created in sandbox/branch with tests.

B-Scale

Specialist handoffs, broader connector networks, and Stripe/public beta packaging wait until core and execution are stable.

North Star

What Phase B should feel like

CubiQo reads everything it already knows before asking a question, builds the task graph, checks access, scores routes, chooses the safest reliable path, executes reversible work, pauses before final actions, shows exactly what will happen, preserves artifacts even on cancellation, tracks cost, learns from outcomes, reports its own health, and proposes fixes in a branch with user sign-off. It never auto-publishes, never auto-sends, and never touches production without the user pressing the button.
