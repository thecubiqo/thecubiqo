/api/admin/security/

├── alerts/
│   └── route.ts
│       ├── GET  → List security alerts
│       │         - Filters: severity, status, type, date range
│       │         - Sorting: by any field
│       │         - Pagination: page, limit
│       │         - Stats: by severity, by status
│       │
│       └── POST → Create security alert
│                 - Validation: alert_type, severity
│                 - Auto-log to audit_logs
│                 - Uses RPC: create_security_alert()
│

        │

                  - Auto-create brute force alert at 5 attempts
                  - Severity escalation: low → medium → high

SECURITY MODEL
═══════════════════════════════════════════════════════════════

Authentication Flow:
  1. User logs in → Receives JWT token
  2. Token stored in cookie (httpOnly, secure)
  3. All API requests include token in Authorization header
  4. API validates token with Supabase Auth
  5. If invalid → 401 Unauthorized

Authorization Flow:
  1. API fetches user profile from database
  2. Checks is_admin flag
  3. If is_admin = false → 403 Forbidden
  4. If is_admin = true → Allow request

Audit Logging:
  1. Every admin action logged to audit_logs
  2. Logged data:
     - Admin user_id and email
     - Action type (user_viewed, user_updated, etc.)
     - Action details (what changed, who was affected)
     - IP address (optional)
     - User agent (optional)
     - Timestamp
  3. Audit logs are immutable (INSERT only)
  4. Only admins can view audit logs

Input Validation:
  1. UUID format validation (regex)
  2. Required field checks
  3. Enum value validation (severity, status)
  4. Type checking (boolean, object, string)
  5. Sanitization (prevent SQL injection)

Brute Force Protection:
  1. Track failed logins per email/IP
  2. 10-minute rolling window
  3. Count attempts in window
  4. Severity escalation:
     - 1-2 attempts: low severity
     - 3-4 attempts: medium severity
     - 5+ attempts: high severity + critical brute_force alert


ERROR HANDLING STRATEGY
═══════════════════════════════════════════════════════════════

Error Types and Responses:

400 Bad Request
  ├─ Invalid UUID format
  ├─ Missing required field
  ├─ Invalid enum value
  ├─ Invalid data type
  └─ No fields to update

401 Unauthorized
  └─ No valid JWT token

403 Forbidden
  └─ Valid token but is_admin = false

404 Not Found
  ├─ User not found
  ├─ Session not found
  └─ Alert not found

500 Internal Server Error
  ├─ Database query error
  ├─ RPC function error
  └─ Unexpected exception

All errors return consistent format:
{
  "success": false,
  "error": "Human-readable error message"
}

Server-side logging:
- All errors logged to console
- Includes stack trace (development)
- Includes user context (user_id, email)
- Includes request details (endpoint, params)


PERFORMANCE CONSIDERATIONS
═══════════════════════════════════════════════════════════════

Pagination:
  - Default: 50 items per page
  - Max: 100 items per page
  - Use offset/limit for database queries
  - Return total count for frontend

Indexing:
  - security_alerts: indexed on type, severity, status, created_at
  - user_activity_log: indexed on user_id, session_id, type, created_at
  - profiles: indexed on is_admin
  - sessions: indexed on user_id, expires_at

Query Optimization:
  - Use SELECT only needed columns
  - Limit results (50, 20, 10 depending on use case)
  - Avoid N+1 queries
  - Use EXPLAIN ANALYZE for slow queries

Caching (Future):

  - Cache top offenders list (5-minute TTL)
